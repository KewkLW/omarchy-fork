# AI

Omarchy treats AI coding agents as first-class citizens, but it doesn't pick a favorite for you. Instead, every major coding-agent CLI comes pre-wired as a lazy-loaded launcher. The launchers are tiny [mise](https://mise.jdx.dev/)-managed stubs in `~/.local/bin/`, so nothing is downloaded until the first time you actually run one. Invoke any of these and authenticate when prompted:

| Command    | Agent                                                            |
|------------|------------------------------------------------------------------|
| `claude`   | [Claude Code](https://code.claude.com/docs/en/overview)          |
| `codex`    | [OpenAI Codex](https://github.com/openai/codex)                  |
| `opencode` | [OpenCode](https://opencode.ai/)                                 |
| `gemini`   | [Google Gemini CLI](https://github.com/google-gemini/gemini-cli) |
| `copilot`  | [GitHub Copilot CLI](https://github.com/github/copilot-cli)      |
| `crush`    | [Crush](https://github.com/charmbracelet/crush)                  |
| `grok`     | Grok CLI from xAI                                                |
| `pi`       | [Mario Zechner's Pi](https://github.com/badlogic/pi-mono)        |
| `omp`      | [Oh My Pi](https://github.com/can1357/oh-my-pi)                  |
| `hermes`   | [Hermes](https://hermes-agent.nousresearch.com/), Nous Research's agent  |
| `muse`     | [Muse Code](https://dev.meta.ai), Meta's coding agent           |
| `cursor-agent` | [Cursor CLI](https://cursor.com/cli)                         |

To wrap an additional CLI the same way, run `omarchy-mise-install <package> [command-name]`. The stubs are kept current along with everything else mise manages when you run `omarchy update` (or the `mup` alias).

### The default agent

Pick your default agent with `omarchy default agent <name>` or under _Setup > Defaults > Agent_ in the Omarchy Menu (`Super + Space`). If the agent isn't installed yet, picking it installs it first. A fresh Omarchy will invite you to make this choice with a one-time notification.

[Muse Code](https://dev.meta.ai) — Meta's `muse` — uses a preinstalled mise stub like the other agents. Picking it as the default installs Meta's official launcher through mise's HTTP backend. The launcher verifies and updates the native binary for your machine.

Once you've chosen, `Super + Shift + Ctrl + A` launches the default agent in a dedicated terminal window (or brings up the picker if you haven't chosen yet). You can also launch it straight into a task with `omarchy agent prompt "Review this project"`. Agents launched this way run unattended in their respective don't-stop-to-ask modes, so be ready for them to actually do things! And since agents refuse to remember trust for your home directory, launches from `$HOME` start in `~/Work` instead.

There are terminal shortcuts too: `a` runs the default agent inline in the current terminal, while `c`, `cx`, and `cy` start OpenCode, Claude Code, and Codex directly (again in their auto-approving modes). Theme changes sync to the agents as well: Claude Code, Pi, OpenCode, and Hermes (once Hermes Desktop is installed) all follow along when you switch the Omarchy theme.

### The agents panel

The top bar grows an agents icon the first time Omarchy finds AI coding usage on the machine (and stays out of the way until then). The panel behind it tracks every subscription in one place: your plan, the percentage used of the 5-hour session and weekly limits (or the remaining prepaid balance), and token usage by day and by model. Claude Code, Codex, and Fireworks are covered out of the box.

Left-click the bar icon for the panel, right-click to launch your default agent. The usage records behind it are regenerated every 15 minutes by `omarchy agent usage-update`, and the panel can even merge usage from your other machines via a synced folder. See the README under `$OMARCHY_PATH/shell/plugins/agents/` for the full settings.

### The agent room

When you run more than one agent, they can talk to each other directly, and you can watch the whole conversation and join in. Agents launched from `Super + Shift + Ctrl + A`, the menu, or `omarchy agent prompt` open on workspace 9, the agent room. It holds only agent terminals and the room pane, so you can glance over and see what your agents are doing. The `a` shortcut and the Quake console keep the agent where you are, but it joins the room just the same.

Agents find each other with `omarchy agent list` and talk with `omarchy agent send`, and the shipped Omarchy skill teaches them how. A message goes straight into the other agent's prompt, headed with who sent it and how to answer, so the agent picks it up right away, even when it's idle.

Open the room pane on workspace 9 with `Super + Alt + A`, _Trigger > Agents > Agent Room_, or `omarchy agent room`. Everything agents say to each other and to you shows up there, and you can talk into it:

- a plain line speaks to every agent
- `@reviewer look at the auth change first` speaks to one agent, by its name or id
- `@claude-5720/a3ed7631 hold off` passes a message to a Claude subagent through its agent
- `/agents` lists who's in the room
- `/pause` stops agents messaging anyone (you can still talk to them), and `/resume` lets them carry on

While the room pane is open, every Claude Code subagent that's at work (the background agents Claude lists under `main`) gets a terminal of its own on workspace 9, showing its task, the commands it runs and what comes back, and closing a minute after it finishes. They open without taking you there. `omarchy agent list` shows subagents under their agent, and `omarchy agent watch <agent>/<subagent>` opens one by hand. Subagents run inside their Claude, so you speak to one through it.

When an agent needs you, `omarchy agent send user` pops a notification and shows in the room. Agents that answer each other in a loop are stopped after 10 messages a minute. An agent you started by hand (`claude` in any terminal) can talk in the room but can't be spoken to, because only agents launched through Omarchy run under the relay that types messages in.

Windows your agents open go there too, whichever agent opened them and however: a terminal an agent starts (another agent, a server, a build) lands in the room, and anything else an agent opens, a browser or an app, lands on the seat's workspace, 10. They arrive without taking you with them, so you keep working where you were. Windows your own rules place, like a game on its own workspace, keep their place, and an agent you start yourself stays where you started it. Turn this off with `require("default.hypr.agent-workspaces").set({ route_spawned = false })`.

The room is workspace 9 unless you move it: add `require("default.hypr.agent-workspaces").set({ room = 7 })` to `~/.config/hypr/hyprland.lua`. If each of your monitors has its own bank of workspaces (1–10 on one, 11–20 on the next), `set({ per_monitor = 10 })` gives every monitor its own agent room, 9 on the leftmost, 19 on the next, and agents open in the room of the monitor you're working on. Monitors count from the left; list their names with `monitors = { "DP-3", "DP-2" }` to count them in another order.

Everything said in the room is kept in `~/.local/state/omarchy/agents/log/` for 30 days, readable only by you. `omarchy agent log` shows today's conversation, and `--all` shows every kept day.

The room is private to your user account: there is no network listener, and apps on the agent seat can't reach it. Each message is stamped with its real sender, and the skill tells agents to treat a message from another agent as a colleague's request, not an order from you. But agents running with approvals off can ask each other to do things, and anything running as you can reach the room. Keep an eye on workspace 9, and pause the room if a conversation goes somewhere you don't want.

### Crash diagnosis

Omarchy watches systemd-coredump for process crashes. When something segfaults, you'll get a "Process crashed" notification — click it, and the crash is handed to your default agent along with Omarchy's diagnose-crash skill, which walks the agent through establishing the facts from the core dump and deciding whether the crash is worth reporting upstream. You can also run it by hand against any PID from `coredumpctl list` with `omarchy agent crash <pid>`.

The watching is on by default. Turn it off under _Trigger > Toggle > Crash Capture_ (or with `omarchy toggle crash-capture`) and the notifications stop; `omarchy agent crash <pid>` still works by hand.

### The agent seat

When an agent needs a graphical app, to click through a web page, fill a form or check how a UI renders, it gets its own seat instead of borrowing yours. Apps started with `omarchy agent seat run` (for example `omarchy agent seat run chromium https://omarchy.org`) open on the agent seat's workspace, 10 by default, with an orange outline, and the agent drives them with its own pointer and keyboard. Your cursor never moves and your focus never changes, so you can keep working while it does.

The apps are real windows in your session, but they run sandboxed: they get their own home under `~/.local/share/omarchy/agent-seat/home`, and they can't reach your other windows, screen, keyring, or input. Your clipboard works in them for you: paste in and copy out as usual. The agent can't use it, so it never sees what you've copied, and nothing it copies lands on your clipboard. Your own mouse and keyboard still work on them: when an agent app needs you, to log in somewhere or solve a captcha, jump to it with `Super + Ctrl + Alt + A` (or _Trigger > Agents > Agent Seat_) and use it, even while the agent carries on in another window. The agent's pointer and keyboard never reach anything outside the seat. `omarchy agent seat stop` (or _Trigger > Agents > Stop Agent Seat_) closes everything on it.

Anything else your agents open, outside the seat, lands on that workspace too: a browser or an app an agent starts arrives there without taking you with it, while terminals an agent starts go to the agent room's workspace, 9. Windows your own rules place, like a game on its own workspace, keep their place. Turn this off with `require("default.hypr.agent-workspaces").set({ route_spawned = false })`.

To put the seat on another workspace, add `require("default.hypr.agent-workspaces").set({ seat = 8 })` to `~/.config/hypr/hyprland.lua`. If each of your monitors has its own bank of workspaces (1–10 on one, 11–20 on the next), `set({ per_monitor = 10 })` gives every monitor its own agent workspaces, 10 on the leftmost, 20 on the next, and seat apps open on the one for the monitor you're working on. Monitors count from the left; list their names with `monitors = { "DP-3", "DP-2" }` to count them in another order.

To use another workspace, add a later window rule at the bottom of `~/.config/hypr/hyprland.lua`. For example, this sends future agent apps to workspace 9 instead:

```lua
o.window("agent-[0-9]+(\\..*)?", { workspace = "9 silent" })
```

Use that workspace's shortcut when you want to interact with an agent app; for workspace 9, that is `Super + 9`. The rule applies when an app opens, so it does not move agent apps that are already running.

Agent apps get no GPU unless you say so. When an agent launches one that needs it, such as a game engine, Omarchy asks you in a menu first: allow it once, allow it for the rest of the session, or deny it. Only an app you allowed gets the graphics card. Your files work the other way: an agent app sees none of them unless the agent shares a folder when it launches the app, and that is up to the same permission rules you gave the agent for your files.

#### Driving your own windows

Sometimes an agent needs a window that isn't on its seat: a terminal you already have open, an editor, an app that only runs unsandboxed. `omarchy agent desktop` lets it take a screenshot of that window, send it text and key combos (`omarchy agent desktop key 0x1234 ctrl+l`), or close it, without moving your cursor or your focus. `omarchy agent desktop list` shows your windows and what the agent may do with each. It can't click or scroll: Hyprland only clicks by moving your pointer, so pointer input stays on the agent seat.

Windows on the agent workspaces (9 and 10 by default) are fair game. For any other window, Omarchy asks you in a menu first: _Allow once_ covers that one command, _Allow until the window closes_ marks the window with an orange outline and covers it until you close it, and _Deny_ refuses. A window on an agent workspace is judged by where it is on every command, so moving it back to your own workspace takes it out of the agent's reach. Keys never go to the window you're typing in, and password managers are never allowed. Change that in `~/.config/hypr/hyprland.lua`:

```lua
require("default.hypr.agent-workspaces").set({
  drive = {
    extra_workspaces = { 7 },
    always_allow_classes = { "^org\\.example\\.Editor$" },
    never_allow_classes = { "^1[Pp]assword$", "^Bitwarden$", "^signal$" },
  },
})
```

`never_allow_classes` replaces the default list, so keep the password managers in it.

This policy is a guard rail for an agent that follows it, not a sandbox. The agent runs as you, so the policy file, the window's mark and the window's workspace are all things it could change itself with `hyprctl`. Omarchy's skill tells agents to use `omarchy agent desktop` and never raw `hyprctl`, and an agent that follows it stays inside the policy. To keep an agent away from your windows for certain, rely on its harness's own sandbox or permission rules.

### Memory emergencies

Agents that run builds, editors and test suites in parallel can fill RAM and swap fast, and when that happens systemd-oomd kills whole groups of processes, sometimes the entire desktop session with every window in it. The memory watchdog steps in before that. It is off by default; turn it on under _Trigger > Toggle > Memory Watchdog_ (or with `omarchy toggle memory-watch`).

When memory is nearly full, the watchdog runs your default agent headless (Claude Code or Codex) with the memory-emergency skill. It works out which AI agents started the heavy processes and messages them first, asking what the processes are for and telling them to cut back to one heavy job at a time. Claude Code sessions receive these messages directly. At the same time it asks you with two notifications: approve its plan, or tell it to stand down. If the agents clean up, it does nothing more. If nobody answers, it applies the safest fix it can: it kills restartable work such as builds and headless editors, only pauses anything that might hold unsaved work, and never touches the session or games. Either way it leaves a report in `~/.local/state/omarchy/memory-watch/reports/`.

If swap gets close to the point where oomd kills, the watchdog pauses the largest process group straight away, without waiting for the agent. Paused processes are stopped, not killed; `omarchy memory resume` brings them back. `omarchy memory top` shows what is using memory by process group, and `omarchy memory agents` shows it per AI agent.

### Desktop apps

The _Install > AI_ menu also carries a few graphical AI apps: the ChatGPT desktop app, Grok Bot for chatting with xAI's models, Hermes Desktop, OpenClaw, and the Perplexity desktop app.

Hermes Desktop is the one to know about, because there is only ever one Hermes on a machine. The app only runs against a runtime built from its own commit, so it installs one of its own under `~/.hermes` on first launch, which takes a few minutes and shows its own progress. From then on that is the Hermes the terminal `hermes` command and the default agent use too, whichever order you installed them in. Installing it also hands Hermes the Omarchy theme as a skin named `omarchy`, which every Hermes surface follows as you switch themes; pick another under Hermes' Appearance settings or with `/skin` if you'd rather it didn't, and Omarchy leaves that choice alone. Removing the app under _Remove > AI_ takes that runtime with it, and keeps your chats, memories, and the skills Hermes wrote for itself unless you tell it otherwise: it asks, defaulting to no, whether that data and your connection settings should go too.

OpenClaw's desktop experience is its Control UI, which opens as a web app backed by its own local gateway. OpenClaw updates arrive through Omarchy's package updates, so skip the Control UI's own "Update Gateway" button: it would try to write into the package-managed install and fail. Removing OpenClaw under _Remove > AI_ takes the gateway service and the app with it and then asks whether `~/.openclaw` should go too, since that holds your chats and credentials alongside the plugin runtimes OpenClaw downloads for itself; the default keeps it.

### Local LLMs

Omarchy recommends two ways of running local LLM models: LM Studio and Ollama. LM Studio provides a GUI interface for finding open-weight models, installing them, and running them. It's a great way to get going easily. Ollama offers a CLI for doing so similarly. But if you're new to local models, I'd start with LM Studio. You can install either under _Install > AI_ in the Omarchy Menu.

### The Omarchy Skill

Agent skills help AI use specific tools in a specific way, and Omarchy ships with a default skill for tailoring the system. Like tweaking your Hyprland config, adjusting the bar, or even creating a new theme from scratch. It's symlinked into the skill directories for Claude Code (`~/.claude/skills`), Codex (`~/.codex/skills`), Pi (`~/.pi/agent/skills`), Hermes (`~/.hermes/skills` and each `~/.hermes/profiles/*/skills`), and the generic `~/.agents/skills` location, so most harnesses pick it up automatically.

But you should treat this skill as experimental. Different models will use it to different effect. It's best to run in plan mode first, so you have an idea of what the agent would like to change. And then be ready to rollback changes or even invoking `omarchy reinstall configs`, if the agent makes a mess of everything.
